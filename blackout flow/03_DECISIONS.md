(4) **Rules version**: every new simulation is stamped with `RULES_VERSION` (now 2, immutable column `rulesVersion`); the server refuses any simulation whose version is missing or different (`rules_version_unsupported`) before reading its log, and the page shows such runs as "earlier rules" without folding or scoring them. | D-011 | 2026-11-18 | Multiplayer architecture (extends D-008; no rule of D-009/D-010 changed, `RULES_VERSION` stays 2). (1) **Lobby as a second append-only log.** A team room is an immutable `team_rooms` row (host, invitation code, rules version) plus the log `team_room_events` (joined, left, role claimed, role released, started, abandoned), one row per `(roomId, seq)` under `uniqueOn`. Membership and roles are a pure fold of that log (`src/game/lobby.ts`); each command validates against the fold and appends one event at `lastSeq + 1`, re-reading and re-deciding if it loses the insert — the mechanism of D-008. The row also carries a server-written view of the fold (status, members) for clients to read; it is never read to decide anything and is rewritten until it matches the log. (2) **Rooms.** Any signed-in user can create one; joining needs the 12-symbol invitation code (60 random bits from `crypto.getRandomValues`, Crockford alphabet). At most three members; one role per member and one member per role; the host alone starts (only with all three roles filled) or closes the room, and has no other privilege; nothing about membership or roles changes after the start. States: lobby, active, completed (derived from the simulation log or the deadline), abandoned (lobby only). Solo mode is unchanged and separate. (3) **Game authorization.** A started room is a simulation whose id is the room id and whose clock starts at the `started` event. Every game command resolves the caller's single role from the lobby log and passes it to the engine, which refuses other roles' actions. (4) **Approvals.** In a team, `requestApproval` records `approval_requested`; the commander answers with `decideApproval`, which must name the operation and the sequence number of the pending request event. Anything else — non-commander, unknown or already-decided request, an older request's number, another room — is refused and writes nothing. (5) **Read access.** Rows list who may read them: `simulation_events`, `team_rooms` and the new `simulation_findings` use the SDK's `read: 'collaborator'` with a JSON array column of user ids, checked by the room per row on every query and every live broadcast (verified in the installed deepspace 0.44.2 source and on the local worker). `team_room_events` is readable by no client. No client role can write any game collection. (6) **Findings.** In a team, text revealed by an event is not stored on the shared event. It is a `simulation_findings` row: incident reports and the closing confirmation are for the team; what an action turns up is private to the participant who ran it until they share it with `shareFinding` (owner only; the server copies the text; idempotent). Sharing is not a game event and does not affect the outcome or score. (7) **Presence** (`usePresenceRoom`) shows who has the room open and grants nothing. | RecordRoom gives per-collection role permissions and per-row owner/collaborator reads, not game roles, so game roles live in the lobby log and are enforced in the server actions (which run with RBAC off and therefore check membership themselves). Reusing the unique-sequence log means the multiplayer invariants rest on the one SDK guarantee already verified (a uniqueness check and its insert are one synchronous step in the Durable Object); no new primitive, no transaction. Tradeoffs: an event and its finding are two writes (the finding is recomputed from the log and written on the next sync if lost); the room view can briefly lag the log; approval requests have no time limit of their own — they stay pending until decided or the simulation ends, because a timeout would be a rule change; a commander who never returns blocks the three gated actions (no reassignment, by instruction); the invitation code has no rate limit or expiry; lobbies are never cleaned up; presence scope names are not access-controlled. | Proposed — awaiting owner acceptance | G,I,L |
| D-012 | 2026-11-18 | Reliability and abuse hardening (extends D-008 and D-011; no rule, role or score of D-009/D-010 changed, `RULES_VERSION` stays 2). (a) **Server timer:** each simulation gets one `settle-simulation` job in the SDK JobRoom `app:<appId>` (persisted in the Durable Object, run from its alarm); each run calls the same settling code a sync uses, then re-queues itself for the next due instant. Settling on the next request (D-008) stays as the fallback. (b) **Sweep:** an SDK CronRoom task `room-sweep` every 10 minutes expires idle lobbies, finishes started rooms past their deadline, and deletes lobbies closed 7 days or more that never started. A room that started is never deleted. (c) **Lobby expiry** is a server-written lobby event `expired`, stamped exactly 24 h after the lobby's last event, whoever notices first. (d) **Limits** per account in fixed windows, counted by unique rows in a closed `rate_slots` collection: 120 rooms/hour, 240 solo simulations/hour, 120 invitation-code attempts/10 minutes (every attempt counts, before the code is looked up). A lobby log is capped at 200 events. Action bodies are capped at 4096 bytes and must be a JSON object. (e) **Other doors:** presence only for `team:<roomId>` scopes and only for that room's signed-in members; scheduler and job-queue sockets admin-only; the job queue accepts no socket writes. (f) **Page:** the answer to a sync is used when live rows lag; lost connection and ended session are stated and recoverable; a retried command keeps its command id. (g) A development-only action `debugSweepRoom` (host only, one room, shifted clock) exists for tests; it is compiled out of production builds. | Uses only primitives found in the installed deepspace 0.44.2 (JobRoom, CronRoom, `uniqueOn`, bounded body reader). Timers add no new source of truth: a job only calls the idempotent settling code, so a lost, late or duplicated job cannot double an event or move a timestamp. Tradeoffs: fixed windows allow up to twice the limit across a boundary; limits are per account, not per network address; one job queue and one record room serve the whole app; solo simulations and finished rooms are kept forever. | Proposed — awaiting owner acceptance | G, I, L, M |
